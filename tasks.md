# Tasks

The live work queue for the monorepo. [`plan.md`](plan.md) holds the research and reasoning behind these tasks.

## Conventions

- **IDs.** One series per area, numbered in order of creation, never reused:
  `BUG` defects (fixed, except where open), `DEP` dependencies, `OPS` containers and operations, `UI` the SvelteKit UI,
  `REM` appointment reminders, `NOT` patient notifications, `REF` conventions adopted from the reference monorepo,
  `CAS` ideas from care-appointment-success, `QUAL` code quality and tooling (review 2026-10-21), `NEW` new-capability candidates (research 2026-10-21), `DTAC` the NHS DTAC self-assessment
  ([`docs/.../2.0/index.md`](docs/united-kingdom/national-health-service/digital-technology-assessment-criteria/2.0/index.md)), and `REL` release.
- **Sizes.** S is about a day, M a few days, L a week or more.
- **A box is ticked only when** an automated test or a clearly described manual check confirms the acceptance criterion. "Landed" items name that check.
- **Entry shape.** `- [ ] **ID (size), Title.** What and where. **Acceptance:** a testable statement.` Finished entries add **Landed 2026-10-18** and **Deviations, stated plainly**.
- **Three-part changes.** A behavioural change is spec + code + test together (see REF-7).

### Capabilities requested 2026-10-18 (CAP)

Fifteen capabilities (CAP-1 to CAP-11 first; CAP-12 to CAP-15 added the same day) for reducing missed appointments, from the care-appointment-success analysis. Design decisions that apply to all of them:

- **Identity stays upstream.** Demographics remain in `person-service`. Communication preferences, contact reliability and coarse analytics attributes are *PAS-owned* and keyed by `person_id` (`patient_communication_profiles`).
- **Every new column is classified** in `governance/personal-data-inventory.csv` (the test fails otherwise).
- **Nothing sends automatically yet.** Offers, backfill and follow-up create records and events; real delivery is still NOT-3 and consent is still NOT-5. This is deliberate.
- **Support can only be added.** No column, endpoint or query lets a risk indicator reduce a slot, delay a contact or deprioritise anyone (NFR-11); a schema guard test enforces it (CAP-10).

### New-capability candidates, research 2026-10-21 (NEW)

Candidates, not commitments; evidence, sources and caveats in [`plan.md`](plan.md#7-new-capabilities-research-2026-10-21). Each behavioural one is spec + code + test. Nothing here sends a real message until NOT-3, and nothing removes a patient from a list without a person.

- [ ] **NEW-1 (L), FHIR R4 at the edge for Wales and UK Core.** Wales exchanges R4 (FHIR Standards Wales IG on UK Core STU2; `DataStandardsWales-Appointment` with its clinic-code extension); the PAS speaks only R5. R4 read endpoints for Appointment, Encounter, ServiceRequest and the waiting-list entry, conforming to a pinned IG version; R5 stays inside. **Acceptance:** responses validate against the pinned Wales IG package with the HL7 validator in CI.
- [ ] **NEW-2 (M), waiting-list validation campaigns.** Builds on CAP-8: a cohort chosen by a named person; a message, then a letter for anyone with no mobile or no reply; a deadline; "no longer needed" removes only when a person confirms; a letter to patient and referrer; reinstatement on request; validation removals counted apart from treatment in reports. **Acceptance:** no patient leaves the list without a named person's confirmation (test); a silent patient gets a letter, not a removal (test); the report separates validation removals (test).
- [ ] **NEW-3 (M), patient-initiated follow-up (PIFU) and See on Symptom.** A follow-up outcome with a window, the conditions written for the patient, a request route through reply links and texts, a person's review at expiry (discharge or extend), uptake reported apart from discharges; urgent-pathway services excluded unless a clinician says otherwise. **Acceptance:** a request inside the window creates a booking task (test); expiry creates a review task and never discharges by itself (test); a request after expiry goes to a person (test).
- [ ] **NEW-4 (M), event subscriptions.** Topic-based FHIR Subscriptions (R5 native, R4 Backport for NEW-1) for appointment, waiting-list and referral changes, delivered from the existing outbox with retries and signed webhooks; subscribers registered by an administrator. **Acceptance:** a change is delivered once to each subscriber, retried after a failure, and survives a restart (database tests).
- [ ] **NEW-5 (M), interpreter need and booking.** Record language, BSL or deafblind interpreting need on the communication profile; a booking for such a patient creates an interpreter request (a staff task; WITS has no API found) and may lengthen the slot; a day-before list shows unconfirmed interpreters. **Acceptance:** booking creates exactly one request; cancelling cancels it; the day-before list includes an unconfirmed one (tests).
- [ ] **NEW-6 (M), reasonable adjustments as a coded record.** Coded impairments and adjustments, shaped like the NHS England Reasonable Adjustment Digital Flag (DAPB4019 v2.0.0), extending CAP-4's needs; shown to staff at booking; exposed as a FHIR Flag; classified in the inventory. **Acceptance:** the codes round-trip through the API and FHIR (test); the staff booking view shows them (Playwright).
- [ ] **NEW-7 (M), carer and proxy authority.** A proxy with scopes (receive, confirm, cancel, rebook), a recorded basis and a named recorder, an expiry, revocation; every proxy action audited as the proxy acting for the patient; proxy messages honour the patient's opt-outs. **Acceptance:** a proxy without the cancel scope cannot cancel (test); an expired proxy can do nothing (test); the audit names the proxy (test).
- [ ] **NEW-8 (L), clinic templates and demand and capacity.** Versioned session templates with slot types (new, follow-up, urgent, PIFU) and ring-fencing, changed only with a named approver; a report of required against available capacity and sustainable list size using NHS England's published core model formulas. Not an overbooking solver (plan §7). **Acceptance:** generating slots from a template is reproducible (test); the capacity report matches a worked example from the published model (test).
- [ ] **NEW-9 (M), audit export as FHIR AuditEvent, and read auditing.** Export `audit_log` in IHE Basic Audit Log Patterns form; record who read a patient's records (today only changes are audited), with the retention in `governance/`. **Acceptance:** exported events validate against the BALP profile; reading a patient's appointments writes one read event (test).
- [ ] **NEW-10 (M), a standard scheduling API.** `$find`, `$hold` and `$book` per IHE ITI Scheduling (R4) over the existing rebook options and booking, with the same NFR-11 and clash rules. **Acceptance:** the IHE examples run against the API; a hold expires; a booking through `$book` matches one through the native route (tests).
- [x] **NEW-11 (S), referral triage outcomes. Landed 2026-10-22 (FR-167, FR-168).** Migration 41 (`returned_with_advice` and `redirected` statuses; `triaged_by`, `triaged_at`, `redirected_to_service`, `redirected_referral_id`, with a CHECK that ties them to the status); `ReferralService::triage`; `POST /api/referrals/{id}/triage` (`outcome`, `triaged_by`, `redirect_to_service`). Only a referral still `received` can be triaged (a waitlisted one has a waiting-list entry that a person must deal with first). A redirect creates the new internal referral in the same transaction so the patient is never lost. The advice text is not stored (it is clinical). Booking, waitlisting and closing now refuse an ended referral, and `close` no longer tries to overwrite a triaged status. **Acceptance, as tested:** `tests/new11_triage_test.rs` (5 database tests, one over HTTP), the migration up-down-up test and the personal-data inventory test. **Not built:** a staff page for triage; the WPRS integration (outside the PAS); returning a waitlisted referral. Original text follows. Add `returned_with_advice` and `redirected` (with the new service) to referral status, ahead of any WPRS integration. **Acceptance:** each transition is audited and a returned referral cannot be booked (test).
- [ ] **NEW-12 (L), NHS Wales App feed.** Referral, waiting-list status and appointment-change events in the R4 contract (NEW-1, NEW-4). **Needs DHCW onboarding:** no public API documentation was found (2026-10-21). **Acceptance:** a DHCW sandbox receives the events; until then, contract tests against the published profiles.
- [ ] **NEW-13 (M), PROMs milestones.** Emit listed, seen, operated and follow-up milestones for the national PROMs platform. **Needs DHCW and the Welsh Value in Health Centre** for the connection. **Acceptance:** each milestone is emitted once per pathway event (test); the platform's sandbox accepts them.
- [ ] **NEW-14 (M), national channels behind `MessageSender`.** NHS Notify (England) and NHS Wales App messaging as senders, preferred over separate carrier contracts for NOT-3. **Needs onboarding** (NHS Notify is for direct-care senders). **Acceptance:** a sandbox send per channel with secrets from the environment and never logged (the NOT-3 acceptance).

- [ ] **NEW-15 (S), follow-up target dates and the delayed-follow-up report.** A `target_date` on follow-up waiting-list entries; `GET /api/reports/follow-up-delay` in the DSCN 2020/18 shape (booked and not booked, banded by percent past target), with CAP-11's k suppression. Goes with NEW-3. **Acceptance:** an entry waiting 8 weeks against a 4-week target reports 100% delayed; booked and unbooked are counted apart (database tests).
- [ ] **NEW-16 (M), Welsh RTT rules.** Clock from receipt of referral; a could-not-attend is a `Reset` with a reason and a named person; `PAS_RTT_RULES=wales|england`. **Needs the current rules text** from Welsh Government or DHCW (only v7, 2017, was found). **Acceptance:** unit tests compute weeks waited from receipt and from the last valid reset; a second reset for one event needs a person.
- [ ] **NEW-17 (S), clinical priority with a review-by date.** An optional `clinical_priority` (P1 to P4 and the patient-choice category) set by a named clinician, with `review_by` and a list of overdue reviews. It never reorders offers or standby by itself (NFR-11). **Acceptance:** setting it without a clinician is refused; rebooking and standby results are identical with and without it; the `cap10_support_test` guard passes.
- [ ] **NEW-18 (M), group consultations.** A declared capacity above one on group sessions only, an outcome per attendee, and the one-to-one option always offered. Not overbooking: the capacity is declared before booking. **Acceptance:** concurrent bookings never exceed capacity (FR-155's race test extended); a one-to-one slot still holds one appointment.
- [ ] **NEW-19 (M), FHIR bulk export.** `$export` for Appointment and Slot, asynchronous with polling and NDJSON files, under SMART Backend Services, applying CAP-11's rules to any use that is not direct care. **Needs a consumer's agreement** (the National Data Resource or an analytics team). **Acceptance:** kick-off, poll and download pass the open-source bulk-data test kit.
- [ ] **NEW-20 (S), review dates on communication needs.** `needs_reviewed_at` and `needs_reviewed_by` on the communication profile and a list of needs due for review (Accessible Information Standard 2025, step six). **Acceptance:** a profile not reviewed within the configured months is listed; a named review removes it (database test); the inventory classifies both columns.
- [ ] **NEW-21 (S), an honest FHIR surface.** Add `/fhir/metadata` (a CapabilityStatement generated from the routes that work) and either build `POST /fhir/Appointment` or remove it; today it is the Phase 2 503 stub (`api/fhir/handlers.rs:339`). Before NEW-1. **Acceptance:** a test fails when the CapabilityStatement lists an interaction that answers 503.
